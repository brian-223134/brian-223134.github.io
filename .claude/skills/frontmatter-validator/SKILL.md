# Frontmatter Validator

## 목적
Jekyll 블로그 포스트의 front matter와 파일명, 카테고리, permalink가 현재 블로그 규칙에 맞는지 검증한다.

이 스킬은 특히 아래 상황에서 사용한다.

- 새 포스트를 작성했는데 배포 전에 메타데이터를 확인하고 싶을 때
- 파일명 규칙과 front matter가 서로 일치하는지 확인하고 싶을 때
- categories, tags, permalink, date, last_modified_at 설정이 올바른지 검토하고 싶을 때
- 기존 카테고리 구조와 맞지 않는 설정이 들어갔는지 확인하고 싶을 때

## 사전 확인

검증을 시작하기 전에 반드시 아래 파일을 먼저 읽는다.

1. `_data/navigation.yml`
2. `_pages/categories/` 아래 카테고리 페이지들

이 두 곳을 기준으로 현재 블로그의 카테고리 구조와 permalink prefix를 파악한다.

## 입력 대상

검증 대상은 기본적으로 `_posts/*.md` 파일이다.

사용자 요청이 아래 중 하나라면 해당 범위로 처리한다.

- 특정 파일 검수: 해당 포스트 1개만 검사
- 방금 작성한 글 검수: 최근 수정 파일 또는 사용자가 언급한 파일 우선 검사
- 전체 점검: `_posts/` 내 관련 파일들을 순회하며 검사

## 검증 항목

### 1. 파일명 규칙

파일명이 아래 형식을 따르는지 확인한다.

`YYYY-MM-DD-카테고리소문자-번호.md`

검사 내용:

- 날짜 형식이 `YYYY-MM-DD`인지
- 카테고리 식별자가 기존 시리즈명/패턴과 크게 어긋나지 않는지
- 번호가 연재형 포스트라면 기존 같은 시리즈 내에서 중복되지 않는지
- 파일명과 permalink 끝 번호가 서로 일치하는지

### 2. 필수 front matter 필드

아래 필드 존재 여부를 확인한다.

- `title`
- `excerpt`
- `categories`
- `tags`
- `permalink`
- `toc`
- `toc_sticky`
- `date`
- `last_modified_at`

주의:

- 이 저장소의 실제 포스트 스타일을 우선 따른다.
- 템플릿에 있더라도 저장소 전반에서 일관되게 사용하지 않는 필드는 강제하지 않는다.
- 예를 들어 `author_profile`은 템플릿에 있으나 실제 포스트에서 항상 쓰이지 않으면 권장 사항으로만 언급한다.

### 3. 값 형식 검증

각 필드의 값이 아래 규칙을 만족하는지 확인한다.

- `title`: 비어 있지 않고 포스트 주제와 맞는지
- `excerpt`: 한 줄 요약 역할을 하는지, 너무 길거나 비어 있지 않은지
- `categories`: YAML 리스트인지, 기존 카테고리 체계에 존재하는 값인지
- `tags`: YAML 형식이 깨지지 않았는지
- `permalink`: 슬래시 구조가 현재 카테고리 구조와 맞는지
- `toc`, `toc_sticky`: boolean 값인지
- `date`, `last_modified_at`: `YYYY-MM-DD` 형식인지

### 4. 카테고리 구조 일치 여부

`categories` 값이 `_data/navigation.yml` 및 `_pages/categories/`의 구조와 논리적으로 맞는지 확인한다.

예시:

- `Company`는 인턴/회사 글 흐름과 일치해야 함
- `NLP`는 논문 카테고리 흐름과 일치해야 함
- 존재하지 않는 새 카테고리를 front matter에 임의로 추가하면 안 됨

새 카테고리가 필요한 것으로 보이면 자동으로 추가하지 말고 사용자에게 확인을 요청한다.

### 5. permalink 검증

permalink는 아래 기준으로 점검한다.

- 카테고리 구조와 prefix가 일치하는지
- 시리즈 번호가 파일명 번호와 일치하는지
- 기존 같은 시리즈 포스트와 패턴이 일관적인지
- 불필요한 prefix 또는 누락된 segment가 없는지

같은 시리즈의 이전 포스트가 있다면 반드시 함께 확인해서 패턴을 비교한다.

### 6. 날짜 일관성

아래를 비교한다.

- 파일명 날짜
- `date`
- `last_modified_at`

검사 기준:

- 새 글이면 보통 파일명 날짜와 `date`가 같아야 함
- 수정 글이면 `last_modified_at`이 `date`보다 빠르면 안 됨
- 명백히 오늘 작성한 글인데 날짜가 어긋나면 수정 후보로 제안

## 검증 절차

1. 대상 포스트를 읽는다.
2. front matter 블록을 파싱한다.
3. `_data/navigation.yml`과 `_pages/categories/`를 읽어 카테고리 기준을 파악한다.
4. 필요하면 같은 시리즈의 인접 포스트를 읽어 번호와 permalink 패턴을 비교한다.
5. 오류와 경고를 구분해서 결과를 정리한다.
6. 사용자가 수정까지 원하면 최소 수정으로 고친다.

## 출력 형식

출력은 아래 순서를 따른다.

### 이상 없음

```text
검수 결과: 이상 없음

- 파일명 규칙 정상
- front matter 필수 필드 정상
- permalink 패턴 정상
- 카테고리 구조 정상
```

### 수정 필요

```text
검수 결과: 수정 필요

오류
- permalink가 기존 시리즈 패턴과 다름
- 파일명 번호와 permalink 끝 번호가 불일치

경고
- excerpt가 너무 짧아 요약 역할이 약함
- last_modified_at이 누락됨

권장 수정안
- permalink: /intern/company/blitz-dynamics/12/
- last_modified_at: 2026-03-17
```

## 응답 원칙

- 실제 파일 내용에 근거해서만 판단한다.
- 추정이 필요한 경우에는 "가능성이 높음" 또는 "기존 패턴 기준 권장"으로 표현한다.
- 새 카테고리 생성이나 permalink 체계 변경은 자동으로 진행하지 않는다.
- 기존 포스트의 permalink 변경은 SEO 영향이 있으므로 사용자가 명시적으로 요청하지 않으면 변경하지 않는다.
- 문제를 찾지 못했다면 명확하게 "이상 없음"이라고 말한다.

## 자주 걸어야 하는 트리거 예시

아래와 같은 요청에서는 반드시 이 스킬을 사용한다.

- "front matter 검수해줘"
- "이 포스트 메타데이터 확인해줘"
- "permalink 맞는지 봐줘"
- "배포 전에 점검해줘"
- "파일명 규칙 검사해줘"
- "카테고리 설정 이상 없는지 봐줘"
- "date랑 last_modified_at 맞는지 확인해줘"

## 비적용 범위

아래 요청은 이 스킬의 주 목적이 아니다.

- 포스트 내용 요약만 원하는 경우: `blog-post-summarizer` 사용
- 포스트 초안 생성이 목적일 경우: 별도 draft 생성 스킬이 더 적합
- 테마, CSS, 레이아웃 수정 요청: 일반 코드 편집 흐름으로 처리
